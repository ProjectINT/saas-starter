# Дорожная карта

Шаблон собирается «пересадкой»: новый репозиторий, ядро БД пишется заново, UI и утилиты переносятся из проекта-донора модулями с чисткой от домена. Номера этапов в скобках — этапы общего плана переноса.

## Фаза 1. Фундамент ✅

Цель: пустое, но рабочее приложение Next.js, связанное с Supabase, и ядро БД для пользователей и мультитенантности.

- Next.js 16 + TypeScript strict + Tailwind 4, ESLint с правилами донора, Vitest.
- Env-контракт на zod: без переменных `dev`/`build`/`start` не запускаются.
- Клиенты Supabase: browser, server, proxy (`getClaims()`), admin (секретный ключ).
- Локальный Supabase на портах 544xx (не конфликтует с другими проектами), скрипт `env:local`.
- Ядро БД: `profiles`, `accounts` (slug + зарезервированные слова), `account_members`, `account_role`, `role_permissions`, `private.platform_admins`; хелперы `private.has_permission` / `is_account_member` / `can_view_profile` / `is_platform_admin`; RPC `create_account`; хук `private.app_on_account_created`.
- Deny-by-default: отозваны default privileges, явные GRANT, column-level UPDATE, RLS везде, `SECURITY DEFINER` только в `private` с `search_path = ''`.
- pgTAP (67 проверок): белый список функций, негативный тест подделки `user_metadata`, RLS аккаунтов/участников/профилей, инварианты владельца, деактивация.

### Решения фазы 1 (отличия от плана)

| Решение | Почему |
|---|---|
| `uuid` (`gen_random_uuid()`) вместо `snowflake_id` | Нативно для Supabase (`auth.users`, storage-пути, генерация типов), не нужна последовательность и text-ключи |
| Удаление участника — `DELETE`, без `deleted_at` | Членство — это выдача доступа; «мягко удалённая» запись предоставляет доступ, если где-то забыт фильтр. Надгробия для синхронизации кэша возьмём из audit log |
| Хелперы и привилегированные функции в схеме `private` | Рекомендация Supabase: `SECURITY DEFINER` не должен лежать в публикуемой схеме. Клиентский RPC — `public.*` `SECURITY INVOKER`, внутри зовёт `private.*` |
| `platform_admins` в `private`, без доступа из API | Назначение админа только через SQL / service role |
| `profiles.email` (синхронизируется триггером) | Список участников с email без доступа к `auth.users` |
| `accounts.owner_id` + роль `owner` у одного участника | `owner_id ... ON DELETE RESTRICT` не даёт удалить владельца; триггер и уникальный индекс держат роль `owner` только за ним |
| Миграции через `supabase db schema declarative sync` (pg-delta) | В CLI 2.12x `db diff` больше не читает `schema_paths`; pg-delta отслеживает гранты, default privileges, комментарии и триггеры на `auth.users` |
| `auto_expose_new_tables` не трогаем | Флаг меняет baseline локальной БД и отбирает DML у `service_role`; deny-by-default задаём миграцией, одинаково для локальной и облачной БД |
| ESLint 9 | `eslint-plugin-import` из `eslint-config-next` 16.4 падает на ESLint 10 |

## Фаза 2. Аутентификация ✅

Цель: пользователь регистрируется, подтверждает email, входит (паролем или через Google), сбрасывает пароль, создаёт первый аккаунт и попадает в него.

- HeroUI v3 (3.2.7) + next-themes, иконки `@gravity-ui/icons`. Провайдеры: тема, `RouterProvider` (клиентская навигация для `href` в HeroUI), `Toast.Provider`.
- Перенос `LoginSignup/*` с ребрендингом: `AuthShell` (форма слева, бренд-панель справа), экраны входа, регистрации, «проверьте почту», забытого и нового пароля. Название и слоган в `core/config/site.ts`.
- Вход и регистрация вызывают Supabase Auth из браузера; капча встроенная в Supabase (Turnstile/hCaptcha), включается env-переменными и `[auth.captcha]`.
- Письма Supabase Auth (подтверждение, сброс, смена email) ведут на `/auth/confirm?token_hash=…`: токен проверяется на сервере, ссылка работает в любом браузере. Шаблоны в `supabase/templates/`.
- `/auth/callback` для OAuth и стандартных шаблонов; `next` проходит через `safeNextPath` (только относительный путь того же сайта, без петли на страницы входа).
- `proxy.ts`: неавторизованных на `/sign-in?next=…`, для `/api` — 401; вошедших со страниц входа — в приложение. `isPublicRoute` + тесты из донора.
- `/accounts`: нет аккаунтов — онбординг, один — сразу в него, несколько — выбор. `/onboarding`: форма поверх `create_account` (сначала Server Action, в фазе 3 переведена на palistor), slug из названия с транслитерацией кириллицы, ошибки constraint-ов под полями.
- Выход: `signOut({ scope: "local" })` и полная перезагрузка страницы.
- Юр. страницы-заглушки `/terms-of-use`, `/privacy-policy`; страница-заглушка аккаунта `/[account]`.
- Vitest: 54 теста (публичные маршруты, `safeNextPath`, ошибки Auth и `create_account`, пароль, slug, env).

### Решения фазы 2 (отличия от плана)

| Решение | Почему |
|---|---|
| Сразу HeroUI v3 вместо v2 → v3 | Решение владельца. В шаблоне мало UI, отдельная миграция не нужна; этап 12 плана снят |
| `@gravity-ui/icons` вместо `@iconify/react` | Iconify грузит иконки из сети во время работы; gravity-ui — пакет, на котором построены примеры HeroUI v3 |
| Вход/регистрация из браузера, без донорских `/api/auth/signin` и `/api/auth/email-signup` | Встроенную капчу Supabase нельзя обойти прямым вызовом Auth; лимиты Auth считаются по IP пользователя, а не сервера; нет входа через service role |
| Ссылки из писем через `token_hash` и `/auth/confirm` | PKCE-обмен `code` работает только в браузере, где начали регистрацию; `verifyOtp` на сервере — в любом |
| Кнопки OAuth по `GET /auth/v1/settings` | Кнопка появляется, когда провайдер включён в Supabase; нет второго списка в env |
| Выбор аккаунта на сервере (`/accounts`), без `localStorage` | Редирект до рендера; «последний аккаунт» вернётся вместе с переключателем (фаза 3) |
| Тексты на английском, ошибки Auth по коду | i18n — фаза 4; словарь будет ключоваться теми же кодами |
| Yandex SmartCaptcha не перенесена | Supabase Auth проверяет только hCaptcha и Turnstile; Yandex потребует серверной обёртки над входом |
| `email_sent = 30` в локальном `config.toml` | Значение по умолчанию (2 в час) не даёт пройти регистрацию, повторную отправку и сброс локально |

## Фаза 3. Участники и инвайты ✅

Цель: владелец приглашает людей, назначает роли, убирает участников и передаёт аккаунт; приглашённый принимает инвайт по ссылке или из списка на `/accounts`.

- `account_invitations`: email, роль, SHA-256 токена ссылки, срок 7 дней, `accepted_at` / `declined_at` / `revoked_at` (закрытые инвайты остаются историей). Одно открытое приглашение на email в аккаунте; повторный инвайт отзывает прежний. `token_hash` не выдаётся клиентам даже на чтение (column-level GRANT).
- RPC приглашений: `create_invitation` (возвращает токен один раз), `revoke_invitation`, `get_invitation(token)`, `list_my_invitations`, `accept_invitation(id)`, `decline_invitation(id)`. Принять или отклонить можно только с подтверждённым email, совпадающим с приглашённым.
- RPC участников: `change_member_role`, `remove_member`, `leave_account`, `transfer_ownership` (прежний владелец становится admin), `delete_account`.
- Правило рангов: действовать только над участниками строго ниже своей роли, назначать роли не выше своей, `owner` — только через передачу владения. Хелпер `private.member_role`.
- Ошибки RPC — стабильные ключи в `message` (`not_allowed`, `invitation_expired`…), тексты в `core/tenancy/rpc-errors.ts`.
- `npm run db:types` генерирует `core/tenancy/permissions.generated.ts` (тип `Permission`) из `role_permissions`. Сопоставление ролей и прав читается в рантайме: `can(context, …)` на сервере, `useAccount().can(…)` в клиенте.
- `app/(app)/[account]/layout.tsx`: аккаунт по slug (404 для не-участников), `AccountProvider`, переключатель аккаунтов, навигация, тема, выход.
- `/[account]/members`: список участников, меню действий по правам и рангу, подтверждения для удаления, выхода и передачи; диалог приглашения со ссылкой для копирования; открытые инвайты с отзывом.
- `/invite/[token]`: принять/отклонить; при чужом email — предложение выйти и войти под приглашённым (`next` возвращает на ссылку). Закрытые, истёкшие и неизвестные ссылки — отдельные сообщения.
- `/accounts`: ожидающие приглашения показываются всегда; иначе — последний открытый аккаунт (cookie `last_account`), единственный аккаунт или выбор.
- pgTAP: 145 проверок (+78: участники, инвайты, белый список функций). Vitest: 65 тестов (+11: ранги, ошибки RPC, форма инвайта).
- Перевод на palistor `0.0.32` (29.10.2026): страница участников, диалог инвайта, открытые инвайты, ответ на приглашение и онбординг. Store на фичу (`core/tenancy/*-store.ts`) создаётся при монтировании; списки грузятся `defineList`-резолверами через браузерный клиент Supabase, изменения — `supabase.rpc` в `onSubmit`. Server Actions `member-actions.ts`, `invitation-actions.ts`, `create-account.ts` и `invite-state.ts` удалены, страница участников на сервере только проверяет доступ. Одно подтверждение на список вместо трёх на строку; ошибка загрузки списка показывается с кнопкой повтора. Vitest: 83 теста (тесты store: валидация, ошибки RPC в полях, сброс, действия; правило email).

### Решения фазы 3 (отличия от плана)

| Решение | Почему |
|---|---|
| Токен только находит приглашение; принять может лишь пользователь с подтверждённым email приглашения | Пересланная или утёкшая ссылка ничего не даёт. То же правило позволяет показать инвайты на `/accounts` без токена |
| `accept_invitation` / `decline_invitation` по id, а не по токену | Список на `/accounts` не знает токенов; защита — совпадение email, id без него бесполезен |
| Ссылку инвайта копирует пригласивший | Email-модуля ещё нет (фаза 5). Токен хранится хэшем, поэтому показать ссылку повторно нельзя — только пригласить заново |
| Закрытые инвайты не удаляются, а получают отметку времени | История «кто кого пригласил и чем кончилось»; доступ инвайт не даёт, в отличие от членства (там `DELETE`) |
| Admin не меняет и не удаляет других admin | Строгое правило «только ниже себя» без исключений; спорные случаи решает владелец |
| Прежний владелец после передачи становится `admin` | Сохраняет доступ к управлению; понизить его может новый владелец |
| UI фазы 3 и онбординг на palistor `0.0.32`, точный пин из npm (решение владельца 29.10.2026, см. уточнение в разделе 8 общего плана) | Сначала UI был на Server Components + Server Actions + `refresh()`; релиза `0.1.0` не ждём |
| Данные — резолверы списков через браузерный клиент Supabase под RLS, мутации — `supabase.rpc` из браузера в `onSubmit` | Один путь для всего состояния: palistor сам грузит, перезагружает (`reload()`) и показывает ошибки списков. Server Actions дали бы второй источник данных (props сервера), который в store без `useEffect` не попадает. Безопасность та же: RPC проверяет права и ранг, RLS — чтение. Так же устроены формы входа (Supabase Auth из браузера) |
| Store создаётся при монтировании (`useState(factory)`), а не на уровне модуля | Модульный store в Next.js — один на все SSR-запросы и хранит данные прошлого аккаунта. Контекст (`accountId`, router) приходит через `useStoreContext` после монтирования, поэтому на сервере резолверы ничего не запрашивают |
| Навигация и `router.refresh()` из `onSubmit` через `store.context.router` | После передачи владения меняется собственная роль: серверный `AccountProvider` надо перерисовать, сохранив тост и состояние страницы |
| Удаление аккаунта: RPC и тесты есть, UI — в настройках аккаунта (фаза 6) | Место для «опасной зоны» — экран настроек, которого ещё нет |
| Ошибки RPC — ключ в `message`, а не свой SQLSTATE | PostgREST отдаёт `message` как есть; i18n (фаза 4) будет ключеваться теми же кодами |

Находки по palistor `0.0.32` (для следующего релиза):

- Ошибки: лист со значением `null` читается как `""` (после `setValues`, `setter`, прямой записи и `reset()`), хотя тип — `T | null`. В типе `resolve` у `defineList` (и в `ListResolveConfig`) нет `contextDeps` и `options`, хотя рантайм их поддерживает; из-за этого резолверы шаблона возвращают `[]` без `accountId` вместо `contextDeps: ["accountId"]`.
- Пакет: `.js.map` ссылаются на исходники, которых нет в пакете, — Vite/Vitest печатает «Sourcemap points to missing source files» на каждый файл. ESM-сборка с импортами без расширений и без `"type": "module"`: чистый Node пакет не импортирует, только бандлеры.
- API: `onSubmit` не может вернуть ошибки полей (шаблон держит их в листьях `<field>Error`, `validate` и `setter`); `submit()` возвращает `success: true`, если `onSubmit` не бросил. В `onSubmit`/`afterSubmit` нет `notify`/`t` (у резолверов есть `ctx.notify`), `store` там типизирован как `ProxyStore<any>`, `store.context` не типизирован. Конфиг вне `defineList` вообще не проверяется по `ConfigNode`: опечатка `isRequred`, `validate` с чужим типом значения и любая сигнатура `onSubmit` компилируются. Третий аргумент `onSubmit` — родитель группы, а не она сама. Колбэки на корне конфига попадают в тип прокси как поля (пришлось вложить группу).
- Документация: README советует store на уровне модуля — нужен раздел про SSR (store на монтирование, `contextDeps`; ленивый резолвер списка запускается при рендере и на сервере). `validate`/`setter` получают значения родительской группы, а не всего дерева, как сказано в `ConfigNode`. JSDoc `setContext` говорит «заменяет целиком», на деле сливает. Не сказано, можно ли строить несколько store из одного объекта конфига (у flow есть модульные кэши по узлам конфига). Компонент с `useForm`, который не читает полей, перерисовывается на любое изменение store.

Релиз palistor с исправлениями из списка выше (минимум — `null` в листьях, `contextDeps` в типе `defineList`, карты исходников) и обновление пина остаются открытыми: репозиторий palistor сейчас на экспериментальной ветке, релиз — решение владельца. Шаблон работает на `0.0.32` с обходами, описанными в AGENTS.md.

Не сделано и перенесено: E2E «инвайт → принятие → смена роли» (Playwright появится с CI, фаза 8); лимит числа открытых инвайтов — вместе с отправкой писем (фаза 5).

## Фаза 4. i18n и ошибки ✅

Цель: интерфейс на en и ru с переключателем, язык пользователя сохраняется; ошибки сервера и браузера попадают в мониторинг, пользователь видит переведённые сообщения и страницы ошибок.

- next-intl `4.14.9` без локали в URL. Локаль запроса: cookie `NEXT_LOCALE`, иначе Accept-Language, иначе `en`. Список локалей — только `core/i18n/config.ts`. `html lang`, `timeZone` (UTC), `onError` и `getMessageFallback` настроены; явная локаль (`getTranslations({ locale })`) побеждает локаль запроса — для писем получателю (фаза 5).
- Английский подмешан под каждую локаль: пропущенный перевод показывает английский текст, а не ключ; ключ, которого нет нигде, уходит в мониторинг.
- В браузер уходят все namespace, кроме серверных (`Metadata`, `Legal`).
- Ключи типизированы по `en.json` (`AppConfig`), опечатка в `t("…")` — ошибка tsc. Хелперы (валидаторы, `authErrorMessage`, `rpcErrorMessage`, конфиги palistor) принимают корневой `t: Translate`; palistor получает переводчик через `useTranslator` (для `validate`) и `store.context.t` (для `onSubmit`).
- Словари: `messages/dictionary/{core,app}` в формате донора `{ word, tip?, context? }`, 215 сообщений ядра. Русский перевод написан вручную.
- `scripts/i18n.ts` (Node без `tsx`): `build`, `check` (CI), `translate` (OpenAI пачками по 40, ответ JSON). Исправлены проблемы донорского скрипта: при ошибке API ключ остаётся непереведённым (не английским навсегда); правка `word` делает перевод устаревшим (хэш исходника в `translations.lock.json`); перевод с потерянными аргументами или тегами отбрасывается; конфликт namespace ядра и продукта — ошибка.
- Язык пользователя: переключатель пишет cookie и `profiles.locale`; при регистрации язык уходит в метаданные и копируется триггером (только при валидном формате, длина ≤ 35); при входе (пароль, OAuth, ссылки из писем) язык профиля становится cookie, а пустой язык профиля заполняется текущим.
- Ошибки: `untracker` `0.0.1` (точный пин из npm). `core/errors` — `captureException`/`captureMessage`/`flushErrors`; обработчик ставят `instrumentation.ts` (сервер) и `instrumentation-client.ts` (браузер). `onRequestError` отправляет шаблон маршрута, а не URL (в путях токены инвайтов и ссылок из писем). Окно: `error`/`unhandledrejection`.
- Вычистка секретов перед транспортом: ключи вида password/token/secret/authorization/cookie/api key и JWT в строках — в событии и в самом объекте ошибки, который получает SDK.
- Отчёты только о неожиданном: неизвестные коды Auth и RPC, сбой загрузки списков, непредвиденная ошибка `create_account`, ошибки синхронизации языка. Ожидаемые исходы (неверный пароль, занятый slug, `not_allowed`) не отправляются.
- `app/error.tsx` (переведена, повтор через `retry()`, код ошибки для серверных), `app/not-found.tsx` (переведена), `app/global-error.tsx`.

### Решения фазы 4 (отличия от плана)

| Решение | Почему |
|---|---|
| Без локали в URL | Приложение за входом; язык — настройка пользователя. Локаль в URL понадобится только лендингу (опц. модуль) |
| Транспорт по умолчанию — console, без `NEXT_PUBLIC_ERROR_HANDLER` и без SDK Rollbar/Hawk в зависимостях | `rollbar@4.2.0` весит 18,7 МБ (rrweb), а `untracker@0.0.1` объявляет peer `rollbar ^2`; `@hawk.so/nodejs` тянет `axios ^0.21` с известными уязвимостями. Провайдер подключается в `core/config/monitoring.ts` установкой SDK и одной строкой; рецепт в комментарии |
| Обработчик ошибок на `globalThis`, а не глобальная переменная модуля `untracker` | `instrumentation.ts` и код приложения — разные бандлы со своими копиями модулей |
| SDK-перехват uncaught выключен (`captureUncaught: false`), вместо него слушатели окна и `onRequestError` | Одинаково для любого транспорта, без двойных отчётов |
| Ошибки Auth/RPC/валидации — по-прежнему ключи в своих namespace (`Auth.errors`, `RpcErrors`, `Validation`), без каталога `defineErrors` | Серверного кода, бросающего ошибки с кодом клиенту, пока нет; каталог появится вместе с первым API/Server Action, которому он нужен (фаза 5–6) |
| `global-error.tsx` на английском | Он заменяет корневой layout: нет провайдера сообщений и стилей; импорт словарей добавил бы их в бандл каждой страницы |
| Скрипт `i18n:translate` вместо донорского `new-messages`; Node `>=22.18` | Встроенный в Node запуск TypeScript, без `tsx` и `dotenv` (`--env-file-if-exists`) |
| `proxy.ts` уводит вошедшего со страниц входа только на GET | Server Action синхронизации языка вызывается POST-запросом на `/sign-in` сразу после входа; редирект ломал её ответ |

Не сделано и перенесено: письма на языке получателя (фаза 5 — механизм готов), часовой пояс пользователя (`profiles.timezone`, фаза 6), предупреждение React о `<script>` от next-themes в dev (внешняя библиотека).
